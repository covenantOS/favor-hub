# Porting a page to the React app

FavorOS's front end is moving to one React + TypeScript single-page app (decided 2026-10-12). The backend does not change: Pages Functions, D1, R2 and the existing /api routes stay. A page that has not moved keeps serving its Astro page.

## Folder layout

```
app/                     the SPA (Vite, React 19, TanStack Router and Query, zod)
  index.html             the app's one page (served by the middleware, see below)
  vite.config.ts         base /_app/, builds into dist/_app, vitest config
  src/
    main.tsx             providers, query persistence, the fetch hook that refreshes menu counts
    router.tsx           router factory
    routes/              FILE ROUTES. One file per URL. __root.tsx mounts the shell once.
    routeTree.gen.ts     generated by the router plugin. Commit it.
    shell/               rail, top bar, phone bar, Ctrl K, bell, dock, help panel, entity host. Never unloads.
    features/<name>/     one folder per ported page (today/, chat/, ...). Components, hooks, styles.ts
    features/entity/     chips and hover cards
    data/hooks.ts        one hook per API route
    lib/                 api.ts (typed client), query.ts (cache, keys), format.ts (dates, money, names), storage.ts, hubOv.ts, legacy.ts
    test/                vitest unit and component tests
  e2e/run.mjs            Playwright run (desktop 1440 and iPhone), fixtures.ts holds invented data
shared/                  used by BOTH functions/ and app/
  app2.ts                MIGRATED_ROUTES and the opt-in rules
  schemas/*.ts           zod schemas for API answers
functions/_lib/app2.ts   the middleware hand-off
functions/api/hub/app2.ts  the switch (GET, POST, PUT)
```

## How a route reaches people

`MIGRATED_ROUTES` in `shared/app2.ts` lists what the app has built. For a person to get a route from the app, all of these hold: the route is in that list, an admin put it in the hub setting `app2.routes` (comma list or `*`), the person is in `app2.audience` (`admin`, the default, or `all`), they opted in (cookie `hub_app2`), and the request is a browser page load. Every other request gets the Astro page, byte for byte. Someone with no cookie costs no database read.

Switching, as the signed-in person: `/?app2=1` opts in, `/?app2=0` opts out (the account menu has "Use classic FavorOS"). An admin saves settings with `PUT /api/hub/app2` and `{"routes": "/", "audience": "admin"}`. Empty routes turns the app off for everyone.

## Add a route

1. Build the server side first if it does not exist: keep logic in `/api`, keep it small, so the page is a view.
2. Add a zod schema for each answer in `shared/schemas/<name>.ts` and export it from `shared/schemas/index.ts`. Use `.default()` for fields the server may omit and `.passthrough()` on objects the server grows.
3. Add the hook in `app/src/data/hooks.ts`: `useQuery({ queryKey, queryFn: () => api('/api/...', schema) })`. Put the key in `lib/query.ts` `keys`. Writes use `send()` and then `qc.invalidateQueries`.
4. Create `app/src/routes/<path>.tsx` with `createFileRoute('/path/')({ component, staticData: { nav: '<nav id from src/data/areas.ts>', title, layout: 'page' | 'wide' | 'full' | 'bare' } })`. `nav` is what the classic layout took as its `nav` prop, and it picks the area, tabs and help article.
5. Put the page in `app/src/features/<name>/`. Import its stylesheets in a `styles.ts` in the same order the Astro page imported them (the cascade depends on it) and import that from the page component. Reuse the existing class names (`h-card`, `h-btn`, `r2t-*`), do not write new CSS for something that looks the same.
6. Add the route to `MIGRATED_ROUTES` in `shared/app2.ts`. A sub-path (`/chat/general`) belongs to its listed parent.
7. Links to other pages use `NavLink` from `@/shell/NavLink`. It stays inside the app for a served route and does a normal load otherwise.
8. Add a tour step (`src/scripts/tours.ts`), the help article update and a What's new line, as for any feature.

## Rules for components

- Names of people, partners, funds, appeal codes, tasks, requests, meetings, clips and courses are `<EntityChip kind id label />`. The hover card, phone sheet, Ask Brain, Message, Make a task and Send to come with it. Never hand-write a name link.
- Every card sits in `<ErrorBoundary label="..." className="h-card">`. One broken card never takes the page down.
- Loading is a skeleton with the card's final size, never a spinner or empty space. Use the `.r2t-skel` rows or match the card.
- Dates, money, names and counts come from `lib/format.ts`. Do not define `esc`, `money`, `ago`, `initials` again; React escapes text, so there is no `esc`.
- Overlays (sheets, menus) register with `hubOv` (`lib/hubOv.ts`) so the back gesture closes them. The Today sheets in `features/today/day.tsx` are the pattern.
- UI text follows the writing rules: no em dashes, facts only, "partners", no mention of AI.
- Helper scripts from `public/js` that are self-contained load through `lib/legacy.ts` `loadScript` the first time a route needs them. When a route replaces one, delete it from the list and the file once nothing else loads it.

## Data layer

`lib/query.ts` builds the QueryClient: 20 s stale time, refetch on focus and reconnect, no retry on an answer from the server. `nav`, `today`, `kpi` and `day` answers persist in sessionStorage (`favor.app.rq.v1`), so a reload paints the last answers and refreshes behind them. Add a key to the `shouldDehydrateQuery` list in `main.tsx` to persist another one. Bump `CACHE_BUSTER` when a schema changes shape. A successful write through `send()` refreshes the menu counts 1.5 s later.

The notification list (`shell/notices.ts`, `Bell.tsx`) merges /api/hub/notifications, /api/work/reminders, /api/requests/notices, /api/tasks/links/bell and /api/chat/inbox into one grouped list and one badge. Ctrl K (`shell/Palette.tsx`, `paletteSources.ts`) adds people, funds and appeal codes from /api/hub/find, a Mail row, and "Ask Brain: ..." as the last row.

## Tests

- `npm run typecheck` (strict TypeScript for app/ and shared/), `npm run app:test` (vitest), and `npm test` runs both after the server tests.
- Unit tests for schemas, formatting and the menu rules go in `app/src/test/`. Add a fixture to `app/e2e/fixtures.ts` (invented data only, the repo is public) and a schema test for each new answer.
- `npm run build` then `npm run app:e2e` runs Playwright at 1440 wide and on an iPhone against the built app with the API mocked. Add your route's checks to `app/e2e/run.mjs`: it paints, no console errors, a failed card shows its message while the others stay, a screenshot for both sizes. Set `PLAYWRIGHT_BROWSERS_PATH='Q:\work\pw-browsers'`.
- `node tests/app2-route.test.mjs` style tests cover the server hand-off. A route that changes a server answer updates its schema and fixture in the same commit.

## Build and deploy

`npm run build` runs the Astro build, stamps it, then builds the SPA into `dist/_app`. The Pages deploy is unchanged. `npm run app:dev` serves the app on :5180; set `HUB_ORIGIN=https://dash.favorintl.org` and `HUB_COOKIE=...` to read the live API while you work.

## Speed rules (2026-10-12, Will: "obscenely fast")

- The app runs on Preact through its React-compatible layer (`PREACT` alias in `app/vite.config.ts`). Write normal React code and types. Unit tests run on real React, the Playwright run covers the built Preact bundle. Do not import a library that needs React internals without checking it in the e2e run.
- First-screen JS stays under 120 KB gzipped (it is 116 now: preact 10, router 25, query 13, zod 26, app 42). Check the `vite build` output before you merge. Anything heavy loads after the first paint with `import()` or `loadScript`.
- `app/index.html` asks for `/api/hub/nav`, `/today`, `/day` (and `/kpi` for leadership) before the bundle arrives; `lib/early.ts` hands them to `api()`. A new first-screen route adds its path to that script.
- The last `nav`, `today`, `kpi` and `day` answers are restored into the cache before the first render (`restoreCache`) and saved 800 ms after they change. Add a key to `PERSISTED` in `lib/query.ts` to keep another.
- Work the first screen does not need (bell lists, dock socket, search index) waits for `useIdleReady()`.
- Styles: the shell imports only what the frame needs (`styles/shell.ts`). A route's styles go in its feature folder (`features/<name>/styles.ts`), so they load with the route's chunk. Styles for drawers and popups that open later go in `styles/lazy.ts`.
- Built files under `/_app/assets/` are cached for a year (`public/_headers`) and kept by the service worker (`public/sw.js`). Account data under `/api/` is never cached.

## Classic pages inside the frame (LegacyPage)

Every route in `MIGRATED_ROUTES` that has no native file under `app/src/routes/` is the catch-all `routes/$.tsx`, which runs the classic Astro page of that address inside the frame (`app/src/legacy/`). `fetchPage` reads the page's HTML once per build (sessionStorage), `applyHead` adds its page-only stylesheets, `runScripts` evaluates its scripts the way hub-swap.js does, and `leavePage` removes everything the page made (timers, listeners, sockets, observers, body nodes) through `public/js/hub-own.js`. The page's nav id, title, width and top-bar buttons go to `shell/meta.ts`, which the shell reads.

- Which stylesheets and layout scripts to skip or load is read from `dist/_app/layout-assets.json`, built from the pages by `scripts/app-layout-css.mjs`. Do not hard-code versions.
- A page that cannot live in the frame (no `h-body`, or an inline module script) loads whole with `?classic=1`. Full-load pages are listed in `FULL_LOAD` in `shared/app2.ts`.
- To replace a classic page with a native route: add `app/src/routes/<path>.tsx` (it wins over the catch-all), build it from the page's API, and keep the classic page until the native one has a Playwright test.
- `npm run app:e2e:islands [route ...]` loads every migrated page against the live API as the FavorOS Tester and fails on console errors, an empty page or a fallback. It also moves through six routes and checks the shell stayed mounted, with timings.
